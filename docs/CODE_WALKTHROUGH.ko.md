# 시연 설명을 위한 기술 선택과 코드 흐름

## 한 문장 설명

“이 프로그램은 영상의 실제 맥락으로 댓글을 만들고, 기본 브라우저의 전용 창에서 게시한 뒤 결과와 중복 방지까지 책임지는 로컬 대시보드입니다.”

## 왜 이 기술을 썼나

| 기술       | 이 과제에서의 이유                                                               | 실제 코드                                             |
| ---------- | -------------------------------------------------------------------------------- | ----------------------------------------------------- |
| Node.js 24 | 서버와 Playwright를 한 실행 환경에서 운영하고 내장 SQLite를 사용합니다.          | `src/server/index.ts`, `src/server/store.ts`          |
| TypeScript | 영상·초안·프로필·게시 상태를 공통 타입으로 연결해 잘못된 데이터 전달을 줄입니다. | `src/shared.ts`, API 입력은 Zod로 별도 검사           |
| React/Vite | 세 칸의 선택 상태와 진행 상황을 화면에 바로 반영하고 빠르게 수정합니다.          | `src/web/App.tsx`, `vite.config.ts`                   |
| Express    | 화면의 버튼 요청을 수집·AI·게시 작업에 연결하고 로컬 접근 제한을 적용합니다.     | `createApp`, `src/server/app.ts`                      |
| SQLite     | 새로고침·프로그램 재시작 후에도 중복 방지와 하루 한도가 유지됩니다.              | `Store.reserve`, `markSubmitting`, 조건부 고유 인덱스 |
| Playwright | 전용 프로필을 열고 한국어 YouTube에서 실제 입력·게시·확인을 수행합니다.          | `BrowserService.open`, `post`, `verify`               |
| Vertex AI  | 제목·설명·자막·인기 댓글에서 고민과 근거를 추출하고 새 초안을 만듭니다.          | `generateDraft`, `src/server/vertex.ts`               |

## 버튼 클릭에서 화면 갱신까지

1. `App.loadVideos`가 `GET /api/videos`를 호출합니다. `searchVideos`는 최근 공개 검색 후보의 게시 시각을 확인하고 정렬합니다.
2. 영상 선택 시 `selectVideo`가 `POST /api/drafts`를 호출합니다. `collectContext`가 영상 자료·인기 댓글을 수집하고 `generateDraft`가 구조화된 초안을 반환합니다.
3. `validateComment`가 길이·브랜드·링크·해시태그·허위 후기 패턴과 출처 문구를 검사합니다. 수정할 때도 서버에서 다시 검사합니다.
4. `POST /api/posts`는 저장된 초안과 영상을 조회합니다. 클라이언트가 보낸 게시 가능 여부를 신뢰하지 않습니다.
5. `Store.reserve`는 하나의 트랜잭션에서 중복·하루 한도·프로필 상태를 확인하고 작업을 예약합니다. 두 번 클릭해도 하나만 통과합니다.
6. `BrowserService.post`가 기본 브라우저의 전용 창을 열고 작성 계정 확인 → `pressSequentially` → 게시 → 내 댓글 확인을 수행합니다.
7. 각 단계가 DB에 기록되고 SSE `/api/events`가 상태를 보내 React 화면을 갱신합니다.

## 시연에서 짚을 세 가지 판단

**“생성보다 근거가 먼저입니다.”** 자막이 없으면 제목·설명 출처를 표시합니다. 수집하지 못한 장면을 지어내지 않도록 실제 문구와 초안을 연결합니다. 문장의 자연스러움과 후기 여부는 사용자가 마지막으로 검수합니다.

**“버튼 비활성화만으로 중복을 막지 않습니다.”** 프런트엔드의 버튼 상태 외에 DB 트랜잭션과 고유 인덱스를 둡니다. 서로 다른 계정으로 같은 영상을 눌러도 서버에서 차단합니다.

**“실패와 결과 불명은 다릅니다.”** 게시 전 실패는 다시 시도할 수 있지만, 게시를 요청한 뒤 확인하지 못한 작업은 `확인 필요`로 잠급니다. 프로그램을 재시작해도 자동 재게시하지 않습니다.

## Google 로그인과 자동 제어를 분리한 이유

Google은 자동 제어 브라우저의 로그인을 제한할 수 있습니다. `BrowserService.openForLogin`은 `ManualLogin.start`로 기본 브라우저를 일반 실행하여 채널 선택 화면을 엽니다. 이미 열린 전용 창에도 재열기 요청을 전달합니다. `loginCommand`는 macOS에서 LaunchServices로 앱을 활성화합니다. `managed-browser.ts`는 전용 프로필 잠금에 기록된 실제 Chrome PID의 사용자·실행 파일·프로필 경로를 검증하고, 모두 일치할 때만 정상 종료를 요청합니다. OS 실행기나 개인 브라우저는 종료하지 않습니다. 잠금이 해제된 뒤 Playwright가 같은 프로필을 열어 계정을 확인합니다. 검증할 수 없는 프로세스와 Windows 로그인 창은 사용자의 직접 종료를 안내합니다.

`youtube-identity.ts`는 YouTube의 계정 메뉴를 실제로 열어 선택된 채널만 읽습니다. 사이트가 인증을 처리하므로 쿠키·인증 헤더를 서버로 복사하지 않습니다. 브라우저로 전달되는 함수에는 Node 전용 변환 헬퍼가 들어가지 않도록 중첩 함수를 피합니다. `browser-runtime.test.ts`는 실제 `tsx`로 변환한 함수를 독립된 실행 환경에서 실행해 `__name` 직렬화 오류의 재발을 검사합니다. Google 로그인은 됐지만 채널이 없으면 연결 실패와 구분해 `YOUTUBE_CHANNEL_REQUIRED`를 반환하며, 화면의 프로필 카드에 안내를 유지합니다.

`src/server/default-browser.ts`의 `detectDefaultBrowser`가 OS의 읽기 전용 연결 정보를 조회하고, `openDefaultUrl`이 검수 페이지를 시스템 기본 브라우저에 엽니다. `BrowserService.refreshDefaultBrowser`는 기본 브라우저 변경 시 프로필 연결 상태를 해제합니다. Chrome·Edge·Chromium은 감지한 실행 파일을 `executablePath`로 전달합니다. Safari·Firefox 등 연결할 수 없는 브라우저에서는 일반 페이지를 열고 자동 게시 연결을 차단합니다. 이 제한을 숨기거나 다른 브라우저로 자동 전환하지 않습니다.

로그인 자체가 실패한 기존 세션만 계속 재사용하지 않도록 `openForLogin(id, true)`는 새로운 전용 세션 폴더를 선택합니다. 기존 세션은 삭제하지 않고, 브라우저 실행에 성공한 뒤에만 SQLite 설정의 `profileSession`을 바꿉니다. `profileDirectory`는 저장된 세션을 로그인 확인·게시·서버 재시작에 일관되게 사용합니다. 새 창을 열었다는 이유만으로 연결 완료로 처리하지 않으며, 실제 YouTube 채널 확인이 성공해야 게시할 수 있습니다.

## 비밀 값은 어디에 있나

서비스 계정 파일은 저장소 밖에 있고 `.env`에는 경로만 둡니다. 서버 SDK가 인증에 사용하며, 브라우저에는 모델명·인증 상태만 보냅니다. 환경변수 파일, 원본 인증 파일, 크롬 프로필, 운영 데이터는 Git 공개 대상에서 제외합니다. 설명하거나 녹화할 때 `.env`와 인증 파일을 열지 않습니다.

## 검증의 범위

자동 테스트는 댓글 제약, URL 경계, API의 로컬 접근 제한, 중복·한도·재시작·날짜 변경·프로필 순환·성장률 판정과 OS별 기본 브라우저 감지·프로필 분리를 검사합니다. Windows·Linux는 가상 OS 응답으로 검사합니다. 실제 로그인 계정과 YouTube UI의 호환성, 실제 댓글 확인은 별도의 실사용 검증 항목입니다. 테스트를 근거로 실제 게시 완료를 주장하지 않습니다.

## 댓글 삭제와 게시 버튼 안내

`comment-target.ts`는 저장된 영상 ID와 댓글 ID가 있는 YouTube 링크만 허용합니다. `delete-comment.ts`는 댓글 ID·본문·작성 채널이 모두 일치하는 행만 선택하고, 최신순 추가 로딩도 확인합니다. `Store.beginDeletion`이 DB에서 중복 삭제와 동시 게시를 막고, 삭제 요청 직전 `markDeleting`으로 요청 시점을 남깁니다. 삭제 성공 응답 또는 완료 표시와 대상 댓글의 소멸을 함께 확인하며, 중단·불명확한 결과는 자동 재실행하지 않습니다.

`BrowserService.verifyDeletion`은 작성 프로필의 공식 댓글 기록이 비어 있는 경우를 ‘댓글 없음 확인’으로 별도 기록합니다. 게시 이력과 하루 사용량, 영상당 1회 제한은 유지합니다. `youtube-language.ts`는 URL 언어 설정만 신뢰하지 않고 전용 YouTube 화면의 실제 표시 언어를 확인합니다.

`post-availability.ts`는 게시 버튼을 사용할 수 없는 이유를 계산합니다. 같은 영상의 다른 계정 재게시 차단과 다른 영상에서의 정상 게시를 구분합니다. `prepareNextComment`는 초안을 비우고 다른 연결 프로필을 선택하며, 기존 재생성 아이콘은 유지하고 버튼을 강조합니다. 편집 검증 요청의 이전 응답은 최신 입력에 적용하지 않습니다.
